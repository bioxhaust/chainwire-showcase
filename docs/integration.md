# Порядок интеграции Chainwire

Единственная очередь и источник статусов: [status.md](status.md). Требования основаны на [плане владельца](reference/chainwire-brand-plan.md), [аудите материалов и сервера](reference/chainwire-materials-and-server.md) и исходниках корпуса. Снимки оригиналов и SHA находятся в [reference](reference/README.md). Обновления очереди не изменяют исторические свидетельства.

## Неизменные требования текущего задания

- Chainwire — пилотное название. Финальный нейминг не блокирует разработку.
- Вся криптосфера: любые экосистемы, Bitcoin, инфраструктура, DeFi, рынки, регулирование, проекты и возможности. Наличие только Solana-адаптера — ограничение данных, а не продукта. Неизвестная сеть не отбрасывается автоматически; список сетей расширяем.
- RU и EN обязательны. Одна сущность, ревизия и пакет проверенных фактов; отдельные тексты и состояния каждого назначения. Числа, даты, источники и выводы совпадают.
- Первый продуктовый рубеж: реальный источник → сохранённое событие → evidence → страницы RU/EN → независимые доставки Telegram RU/EN → связь с проектом. Макет или локальный тест не означает достижение этого рубежа.
- Повторно использовать Python-бота. Целевая архитектура плана: FastAPI, PostgreSQL с заданиями/outbox, Next.js. Фронтенд собирается вне действующего малоресурсного сервера; размещение решается после замеров.
- Неизвестное отделяется от отрицательного. Качество, риск, полнота данных и срочность — отдельные измерения. Веса методики не объявляются авторскими без эталонов владельца.
- Переходы зависят от готовности и доказательств. Календарные сроки и проценты готовности не используются.

## Владение и рабочие копии

Интегратор `/root` владеет `docs/status.md`, этим документом, `docs/product/scope.md`, источниками требований и решением об интеграции. Он не переписывает файлы активных исполнителей без передачи владения.

- **Research** — `/root/materials` в первой волне: `scripts/materials_manifest.py`, `docs/research/`, `evals/`, позднее `kb.py`, `prompt.py`, `scoring.py`. Изменения runtime только по отдельной карточке. `kb.py` временно передаётся Platform для изоляции путей в CW-002i; CW-001d начинается после её приёмки и возврата владения Research.
- **Platform** — `/root/platform` в первой волне: конфигурация, CI, `db.py`, `storage/`, `migrations/`, `api/`, `docs/contracts/`. Только Platform изменяет общую схему и миграции.
- **News** — назначается перед началом карточки: `discovery/news.py`, `tgchannels.py`, `breaking.py`, `loop.py`, `dual.py`, `publisher.py`, `tgbot.py`, `telegraph.py`, `fmt.py`. Для отображения неизвестного и оценки `fmt.py` временно передаётся Research в CW-001f; затем для сети — Intelligence в CW-005a. CW-005a зависит от CW-001f; после неё файл возвращается News. Другие изменения форматирования до возврата не запускаются.
- **Intelligence** — назначается перед началом карточки: остальные discovery, `enrich/`, `pipeline.py`, `funds.py`, `hot.py`, `tracker.py`. `enrich/scam.py` временно передаётся Research только в CW-001e. Изменения `fmt.py`/`loop.py` проводит News после согласования.
- **Product / Design / Web / Growth** — соответственно `docs/brand/` и `docs/product/` кроме scope; `design/`; `web/`; `docs/growth/`.
- **QA** — независимый от автора проверяющий, `docs/reviews/`, `tests/acceptance/`, эксплуатационные сценарии. Функциональные исправления возвращает владельцу. `ops/` передаётся ему после завершения платформенной CW-002h.

Будущая роль — ответственность за карточку, а не утверждение о запущенном агенте. Перед стартом интегратор записывает конкретного исполнителя, SHA базы, ветку и абсолютный путь worktree в `status.md`. Пока они не записаны, задача не считается «в работе».

Текущие worktrees созданы средствами Git внутри `../worktrees/`: каталог самого чата не является Git-репозиторием, Git-корень — `chainwire/`. Это обычные Git worktrees, не зарегистрированные как управляемые артефакты приложения. Их список проверяется через `git worktree list`. Основной checkout использует `cw/integration`; исходная `main` сохраняет базу.

## Цикл задачи

1. У карточки есть один результат, владелец, разрешённые файлы, зависимости и проверяемая приёмка. Активны максимум два исполнителя плюс интегратор и независимый QA. Одна зона файлов не редактируется параллельно.
2. Исполнитель начинает от принятой базы, работает только в своём worktree, фиксирует изменения коммитом и передаёт SHA, команды, результаты и ограничения. Тесты используют временные БД и заглушки внешних сервисов.
3. QA в отдельной рабочей копии проверяет конкретный SHA, читает diff и повторяет сценарии. Его verdict и доказательства хранятся в `docs/reviews/`. «Тесты автора прошли» без независимого запуска недостаточно.
4. Исправления возвращаются автору; новый SHA проверяется заново в объёме изменений. Общий контракт меняет только Platform, после чего зависимые карточки актуализируются.
5. Интегратор переносит проверенный коммит в `cw/integration`, проверяет совокупный сценарий и только затем отмечает «принят технически». Продуктовая приёмка владельцем указывается отдельно, если она нужна. Ветка интеграции не равна `main` или GitHub PR.
6. Развёртывание — отдельное действие с SHA/образом, окружением, миграциями, smoke-проверкой, доставками по языкам и rollback. Без этих свидетельств поле «развёрнут» равно «нет» или «не проверено» для старого сервиса.

Статусы потока: **очередь → готова к началу → в работе → на независимой проверке → принята**. Допустимы **зависимость** и **заблокирована** с причиной и следующим действием. В каждой карточке отдельно указаны **написан / проверен / принят / развёрнут**; локальная проверка и staging не смешиваются.

## Формат свидетельства

ID задачи; base/head SHA; автор и QA; перечень файлов; точная команда с cwd; результат/число проверок; покрытые критерии; непроверенные границы; verdict. Для публикации — отдельные language, destination, revision и подтверждение внешнего сервиса. Для неизвестного результата Telegram timeout — `uncertain`, а не вымышленное exactly-once или слепой повтор. Для AI — версии данных/промпта и сверка с эталонами.

При ревью удаления `.env` нельзя выводить patch с прежними значениями. Проверяется метадата индекса и только имена полей; секреты не копируются в отчёты. Не запускать бот с рабочими ключами ради тестирования. Исходные tracked SQLite и приватный корпус пока остаются в Git; тесты не используют их как изменяемое окружение.

## Эскалация владельцу

Обычные технические решения принимаются командой. Владельцу передаются конкретные парные RU/EN-образцы для голоса/рубрик, спорные правила с примерами и эталонные оценки, измеренный бюджет платных источников и предложение границ публичного запуска после закрытого прогона. Подготовка этих вариантов не блокирует независимые технические задачи. Ротация доступов — эксплуатационный блокер, а не продуктовая дискуссия.

Обновление владельцу: что принято и чем доказано; что выполняется; точный блокер и следующее действие; только подготовленные решения, требующие владельца. Поддержка этой очереди продолжается при работе в этом чате; фоновый мониторинг или расписание сами по себе не созданы.
